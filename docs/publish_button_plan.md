## 2. 目标与不做的事
目标:所有者在本机后台里能"先看清要发布什么、检查通过后再发布",并留下可追溯记录。
不做:自动发布(定时/提交即发);让访客接触任何发布入口;把会员、行情、`.secret`、后台、工作台内容放到公开站。

## 3. 总体顺序(每步单独审、单独批准)
步骤 0(处置线上现状)→ 步骤 1(先修脚本,不做按钮)→ 步骤 2(导出检查按钮)→ 步骤 3(发布按钮)→ 步骤 4(回退)。**步骤 1 必须先于任何按钮**,否则会把当前未加固的脚本暴露给 Web 入口。

## 4. 各步骤

### 步骤 0:线上现状处置(需要所有者决定,不在本方案内自动执行)
- 线上已有的 `page-ws-*.js` 与内部 mock 数据要不要撤下?撤下需要一次重新发布,属于对外动作。
- 建议:**不手工上传**。等步骤 1 的新流程做好并通过审核后,把"移除这些文件"作为新流程的**第一次真实发布**。在此之前线上保持现状,风险按"信息暴露、非数据泄露"评估(所有者可另行决定更早处理)。
- 重新发布不保证已被缓存/收录的内容消失。

### 步骤 1:先修脚本(不做按钮)
- 复制进仓库 `scripts/build_public_site.py` 并纳入版本控制;**构建模板与资产**(原 `AQ-tools/assets`、`root-index.html`)也一并纳入仓库(或用固定来源 + 哈希),否则迁移不可复现。旧脚本保留不动。
- **相对路径白名单**:`scripts/public_allowlist.json` 逐个列出允许发布的文件(相对路径 + sha256)。不再是"整个 `shared/` + 允许后缀"。新增文件必须显式加进白名单并经审阅,不会自动被纳入。
- **字典按公开键白名单生成**:不按 `adm.*` 前缀剔除,而是只保留公开页面实际用到的键;`ws.nav.admin` 等工作台键自然不在其中。
- **`mock-data/` 逐文件、逐字段**定义允许的合成 schema;来源标记(`_meta`)不能代替内容审核。
- **引用闭包检查**:HTML/JS 引用的资源都必须在白名单内;白名单外的文件一律不导出;禁止残余工作台导航和内部接口路径(`/api/holdings` 等)。
- **全文件处理规则**:未知后缀、符号链接、路径越界、无法解码、sourcemap(及 `sourcesContent`)、`.DS_Store`、隐藏/临时/备份文件(包括具合法后缀的 `backup.js`)一律拒绝;HTML/JS/CSS 注释和内联路径/URL、远端依赖、SVG 脚本与外链按规则扫描;二进制只允许"已批准资产 + 哈希",不是整体豁免。
- **不再 `rmtree` 稳定目录**:每次构建到新目录 `build/<build_id>/`,失败保留上一个有效产物和失败证据;输出路径固定边界,拒绝输入/输出重叠;导入时不构建,输入/输出可在测试中注入临时目录。
- **词表与免责声明检查是辅助**:合规词表(`低风险`、`高收益`、`稳赚`、`保证收益`、`必涨` 等)、字典里必须存在免责声明词条(`pub.synthetic`、`landing.footer.note`)和联系邮箱词条(邮箱待所有者提供)。**词条存在不保证页面渲染出来**,渲染后的页面要用离线浏览器或所有者目视检查,不能用 WebFetch。
- **manifest**:规范化(按 UTF-8 相对路径排序、固定根目录绑定、排除 manifest 自身)、记录大小和 sha256;与"上次已发布 manifest"对比出新增/修改/删除。
- **测试**(`tests/test_build_public_site.py`,临时目录造假 mockups,不读真实 `dashboard/mockups`、不读 `.secret`、不联网):备份文件被拦、后台/工作台文件被拦、未知后缀被拦、符号链接被拦、字典非公开键被剔除、`assets`/根入口也被过滤、公开依赖缺失被拦、失败保留旧产物、manifest 自引用、快照变更被发现。

### 步骤 2:后台「导出并检查」按钮(只读本机,不上传)
- 新增 `POST /api/admin/publish/build`,**每次请求先后检查**:`publish_enabled` 开关 → 完整管理员认证(不能只靠 `_local_or_owner` 或隐藏按钮)→ Host/可信通道 → Origin/CSRF 与 dashboard 请求头 → 才启动任务。
- `publish_enabled` 默认 **False**,缺配置/读取异常也按关闭处理;**不沿用其他"默认开"例外**。关闭后新任务一律拒绝;运行中任务给出明确状态(不强杀,标记为"将在完成后丢弃")。
- 子进程:固定可信可执行文件路径、固定 argv/工作目录/最小环境变量;超时;并发限制(同一时刻只允许一个构建,串行锁);日志脱敏,不把子进程输出或环境变量回传界面。
- 产出:服务端生成唯一 `build_id` 和只读快照目录;返回是否通过、文件数、命中的规则、与上次已发布 manifest 的差异。**没有发布按钮。**

### 步骤 3:后台「发布」按钮(对外动作,最后做)
- **批准对象是 `build_id` 对应的固定快照**,不是客户端提交的哈希。发布前先对**该快照**重新全量枚举、算哈希、扫描;文件集合必须与 manifest 完全一致,拒绝新增/缺失/改动/非普通文件;上传的就是这份快照。快照目录禁止被其他进程写入。
- **状态机**:`created → checked → approved → deploying → succeeded | failed | unknown`;构建/发布受同一把串行锁;重复请求去重并返回同一结果。
- **一次性确认令牌**:服务端生成,绑定 `build_id`、manifest 摘要、目标站点和新增/修改/删除摘要;使用即作废,防旧确认重放和双击。`confirm=true` 不单独构成确认。每次发布都需要所有者在界面上明确确认,不做自动发布。
- **"上次已发布"指针只在上传明确成功并核对后才更新**;失败/超时/结果不明记为 `unknown`,不谎报成功。
- **工具与凭据边界**(重写):
  - 固定可信的 wrangler 可执行文件路径和**精确版本**,不用生产环境的 `npx --yes wrangler@3` 现场解析;wrangler 的安装、版本固定和依赖审查在发布流程之外另行批准。
  - **区分两件事**:"Web 服务进程不解析、不保存、不展示任何 Cloudflare 凭据"可以做到;但**部署子进程使用 wrangler 的登录状态是真实存在的能力边界**(继承环境和用户权限),不能承诺"整个自动发布流程完全不接触凭据"。启用受控部署子进程需要所有者**单独明确授权**。
  - **备选方案(由所有者选)**:Web 服务只做"导出并检查",上传由所有者在终端手动执行(使用同一份已审快照和命令),不在 Web 服务里放任何部署能力。
- 审计:记录谁、何时、`build_id`、manifest 摘要、文件数、结果;不记录凭据。

### 步骤 4:回退
- 回退 = **重新扫描/核对保留的旧静态快照后部署**,不是用当前源文件重新构建一个"旧版"。保存每次发布的目标、内容摘要、成功状态、工具与扫描规则版本;部署成功后核对实际结果再切换本地已发布指针。
- 先要有"可信的此前成功版本"基线,只保留本次新版本不保证第一次回退可用;本地 `AQ-site` 备份不是线上部署版本的证明。
- 重新上传旧版**不保证**旧部署 URL、缓存或已被收录的内容消失;需要另写"紧急停止发布/访问限制/旧产物处置"的预案,平台能力未验证前不得写成已具备。
- 版本保留份数与清理由所有者决定;任何清理都只移动、不永久删除。

## 5. 风险与应对
| 风险 | 应对 |
|---|---|
| 后台/工作台内容或内部接口结构被发布 | 路径白名单 + 字典公开键白名单 + 引用闭包 + 逐字段 mock schema |
| 备份/临时/隐藏文件被上传 | 白名单之外一律不导出,未知后缀直接失败 |
| 校验后文件被改(TOCTOU) | 固定只读快照 + 发布前对快照重验 + 串行锁 + 状态机 |
| 双击/重放/旧确认 | 一次性确认令牌,使用即作废 |
| 凭据暴露 | Web 服务不解析/不保存凭据;部署子进程的凭据使用单独授权,或改为手动上传 |
| 工具被替换/版本漂移 | 固定可执行路径和精确版本,不用 `npx --yes` |
| 误触发布 | 默认关闭 + 两个路由都校验开关与管理员认证 + 每次所有者确认 |
| 合规措辞 | 词表与免责声明词条检查(辅助)+ 渲染后人工检查 |
| 发布后想撤回 | 保留旧静态快照;缓存/收录无法保证撤回 |

## 6. 所有者决定(2026-10-24,聊天中逐项确认)
1. **批准步骤 1**(只修脚本和测试,不做按钮、不上传、不动线上)。
2. 线上已有的内部工作台脚本和合成 mock 数据:**等新流程做好,作为第一次真实发布时移除**,不手工上传。

4. 联系邮箱:**先留占位**(明显的占位值,检查脚本把占位当作"尚未填写"并拒绝发布),以后再给。

## 6.5 步骤 1 的实施结果(2026-10-25,待 Codex 复审)
- 已实现:`scripts/build_public_site.py`(只导出+检查,无上传)、`scripts/public_allowlist.json`、`scripts/public_site/`、`tests/test_build_public_site.py`;详见 `handoff/reports/T020_S3.md`。
- 与 v2 的差异及处理:① 字典/mock/SVG 用 `content_pins` 钉死导出后内容的哈希(冻结基线,改动即构建失败,须重新审阅后更新),代替"公开键白名单 / 字段级 schema";mock 必须带"合成"标记,SVG 禁止主动内容。② 文本文件(非字典/mock/SVG)不逐个钉哈希,靠 manifest 与"已发布"对比。③ 步骤 3 的后台发布按钮取消(所有者决定:上传手动),改为 `--verify` + `--expect-manifest-sha256` + `--mark-published`。

## 7. 本方案的局限
- 线上只用 `curl` 核对了少数文件的状态和内容类型,没有枚举线上全部文件,也没有看渲染后的页面。
- 没评估 Cloudflare Pages 的缓存与回滚细节;wrangler 登录状态如何维持没验证。
- 工作量未估算;步骤 1 的白名单需要逐个梳理公开页面实际依赖的文件,可能比预期长。
